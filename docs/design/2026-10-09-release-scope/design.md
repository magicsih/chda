## 목적·범위·근거

원래 14개 이슈의 코드와 릴리스 검증 절차는 main에 병합돼 있다. 실제 macOS
검수 3회와 두 전체 E2E, 서명된 draft 검증 및 공개는 아직 남아 있다.
추가 #173의 공유 서버 중계는 실제 Codex 0.161.0의 기본 named permission
profile을 보존하지 못해 승인 1.1의 채택 조건이 실패했다. 제품 중계는 없다.

| 선택 | 다음 공개 릴리스의 범위 | 영향 |
| --- | --- | --- |
| A — 원래 14개 릴리스, 권장 | #149–#155, #158–#164. #173은 미해결로 보류 | 실제 검수를 통과한 개선을 공개할 수 있다. Codex 0.161.0의 기존 공유 서버 경고는 남는다 |
| B — #173 해결까지 공개 보류 | 원래 14개와 #173 모두 | Codex의 지원 인터페이스 또는 검증된 새 설계를 기다린다. 해결 시점은 확인되지 않았다 |

두 선택 모두 #14 Windows/Linux 작업은 제외하고 기존 build CI는 유지한다.
A의 권장은 이미 구현한 원래 범위의 공개를 추가 upstream 제약과 분리하기
위함이다. #173을 해결했다고 표시하거나 검수 조건을 낮추자는 제안은 아니다.

## 흐름·구조·책임·데이터

A: 정확한 범위 승인 → 현재 소스·설정 고정 → 독립 검수자를 포함한 실제
macOS 개발 실행 검수 3회 → release-plz 병합 → 최종 SHA의 빌드 전 전체
E2E → 서명·공증된 draft → 실제 launch/update/PID/GUI IPC 확인 → 같은 SHA의
공개 전 전체 E2E → 동일 draft 공개 → 다운로드·Latest·Homebrew·Pages 재확인.

B: 공개 gate를 닫은 채 #173 근거를 유지한다. 새 방식이 준비되면 별도 설계
승인과 보존 검사를 먼저 수행하고, 전체 릴리스 검수를 다시 계획한다.

실행 저장소는 chda 하나다. Codex 설치·전역 config/auth·사용자 daemon을
변경하지 않는다. 기존 PTY 및 업데이트 `prepared/commit` 책임도 유지한다.
새 제품 구조, UI, 저장 형식, 통신 API를 도입하지 않는 범위 결정이다.

## 품질·인수조건·실패

- A를 선택해도 1.0의 14조건과 catalog 전체 기능 검수, 3회 상한, 두 최종
  E2E 및 기존 릴리스 검증기를 그대로 적용한다. 자동 테스트는 native 검수를
  대신하지 않는다. 범위 결정 자체는 문서 변경이므로 TDD 대상이 아니다.
- Codex의 권한·실제 상태·exact resume·동시 pane·child 및 user notify를
  기존 실행 방식에서 검수한다. #173 경고와 그 실행 모드는 알려진 미해결
  항목으로 구분한다. 이것이 원래 기능 조건도 막으면 공개하지 않는다.
- 실제 검수에 실패하거나 source가 바뀌면 결과를 보존하고 해당 검사를
  다시 실행한다. 확인하지 않은 항목을 통과로 만들지 않는다.
- 공개 문구는 검증된 개선만 설명한다. #173 수정 주장은 제외하고 해당
  CLI 버전의 알려진 경고와 issue 링크를 남긴다.

## 적용·운영·복구·승인

이 문서의 정확한 commit과 A/B 중 하나를 승인받는다. 승인 전 PR #167과
release dispatch는 실행하지 않는다. 문서 PR 병합은 범위 변경 승인이 아니다.
승인된 기존 원래 14개 범위의 소스 점검 및 검수 준비는 계속할 수 있다.

신뢰 검사에 사용한 임시 fixture 항목은 제거됐고 다른 사용자 설정 보존을
확인했다. 소유한 조사 프로세스만 정리하며 사용자 앱·daemon은 종료하지
않는다. 서명된 draft 단계까지 Latest와 Homebrew는 바꾸지 않는다. 공개 후
문제가 확인되면 자동 downgrade나 기존 release 덮어쓰기를 수행하지 않고
정확한 영향과 복구 대상을 먼저 확인한다.
